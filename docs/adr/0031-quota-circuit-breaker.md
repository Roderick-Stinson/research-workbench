# ADR-0031：额度熔断 + 预算：撞到限额就停，恢复后自动补跑

- 状态：已接受；第 4 条（token 估算预算）已被 ADR-0032 取代
- 日期：2026-10-12

## 背景
批量模型（第三方 Gemini 接口）有 **5h 与 7d 两级限额**；codex 用本人的 ChatGPT 订阅，同样有窗口限额。
2026-10-12 实测：09:32–12:30 用掉约 1630 万 token（入 1407 万 + 出 223 万）后，5h 额度显示 0%，7d 剩 83%。
本人要求：触发限额后一直请求没有意义。

## 决策
1. **熔断**：批量模型返回限额类错误（HTTP 402/403/429，或错误里有 quota / limit / exceeded / 额度 等）、
   codex 报 "usage limit … try again at …" 时，写 `reports/llm_block.json` / `codex_block.json`（恢复时间能解析就用，否则 30 分钟后试探一次）。
   熔断期间所有进程**不发请求**，直接抛 `LLMPaused`；第一个成功的试探请求解除熔断。
2. **步骤"暂停"不是"失败"**：每日流程的步骤状态记为 paused（带预计恢复时间），推送里单列"⏸ 暂停中"。
3. **自动补跑**：cron 每 30 分钟 `wb daily resume`：熔断已解除就从第一个暂停 / 失败的步骤往后补跑；精读、精选或构思补好了就推送"🔄 更新"；
   然后按预算续跑回填。各步骤的进度都是逐篇保存的，补跑不会重做已完成的。
4. **预算**（`config.json` 的 `llm_budget` 可改）：按工作台自己的用量日志算最近 5h / 7d 的 token；
   每日流程不设上限（以真实限额为准）；**回填最多用到 5h 估计额度的 60%，7d 估计额度剩不到 35% 就停**，保证每日推送有额度。
   估计额度：5h ≈ 1600 万 token、7d ≈ 9000 万 token；每次撞到限额都记进 `reports/llm_limits.jsonl`，用来校准。
5. **精读降耗**：从 9 次调用（每次重发全文）改为 4 次（提纲 + 3 组），正文直接输出 HTML（不再包在 JSON 里，避免转义错误导致的整篇重试）。
6. 顺带发现的旧论文（通过引用等途径）速读走回填预算，不挤占每日流程。
