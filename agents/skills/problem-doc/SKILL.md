# Problem 文档

一个 Problem = 现有方法做不好的一件**具体**的事（ADR-0018）。它的价值全在证据：**不可以猜**。

## 证据只有两种来源
1. **论文**：工作台论文库里的论文（`$WB_HOME/papers/<id>/`：quickread.json 有抽取的数字与出处，fulltext.txt 是全文）。
   引用时写清楚：论文 id、原文句子（英文原句，≤2 句）、表号 / 图号 / 节号、数字。
2. **bad case**：工作台里某个 Run 的逐样本输出（`$WB_HOME/runs/<RUN>/outputs/...jsonl` 或 Run 原始输出目录）。
   引用时写清楚：Run ID、文件路径、sample_id、输入 / 输出 / 标准答案的**原文片段**。

## 图
- **每张图都必须由真实数据画成**：先把数据摘到 `figs/<name>.json`（带来源字段），再用 `figs/<name>.py` 生成 SVG，
  HTML 里内联 SVG，figcaption 写明数据来自哪篇论文的哪张表 / 哪个 Run 的哪些样本。脚本和数据都留着，可复核。
- 示意图（流程 / 机制）可以手画，但必须标注"示意"，且其中出现的具体例子必须是真实样本。
- 不允许为了好看编造数字、编造样本、编造对话。

## 结构（单文件 HTML，中文；可复用 `../paper-explainer/assets/template.html` 的样式，删掉用不到的步骤）
1. **一句话问题**：谁、在什么情况下、做不好什么。
2. **为什么重要**：影响多大（用证据里的数字）。
3. **证据**：按来源分组；每条证据 = 原文 / 样本 + 出处 + 数字。至少 2 篇论文，或 ≥ 3 个 bad case 样本。
4. **图**：≥ 1 张真实数据图（例如各方法在某类样本上的失败率条形图、一条真实轨迹的逐步拆解）。
5. **受影响的方法**：表格 方法 × 是否存在该问题（✓ / △ / ✗ + 证据链接）。
6. **根因假设**：机制层面的解释；标明哪些是证据直接支持的、哪些是推测（推测要写"推测"）。
7. **还不知道的**：现有证据回答不了的问题、需要什么实验来确认。
8. **参考**：所有引用到的论文（id、标题、arXiv 链接）与 Run。

## 质检
- `grep -n '{{' problem.html` 为空；每个数字都能在证据或 figs/*.json 里找到出处。
- 证据不足（少于 2 篇论文且没有 bad case）时，不要写成正式问题：回复 FAILED: 证据不足。
